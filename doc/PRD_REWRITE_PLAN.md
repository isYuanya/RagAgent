# PRD 重构计划：RagAgent 完整产品版

## 1. 当前决策

本次 PRD 重构选择“完整产品版”方向。

这意味着最终产品不只做文案资产入库和拆解，而是要覆盖从文案沉淀到创作辅助的完整链路：

1. 文案入库
2. LLM 拆解
3. 片段级素材沉淀
4. 素材检索
5. 手动组稿
6. AI 推荐下一句
7. AI 自动组稿
8. 文案诊断与评分
9. 原创改写与风险控制

但这里需要明确一个重要边界：完整产品版不是要求第一阶段一次性做完所有深度能力，而是要求最终 PRD 按完整产品形态设计，再把实现拆成多个阶段。

## 2. 两份 PRD 的定位

### 2.1 `PRD.md`

当前 `PRD.md` 的定位更清晰，适合作为近期工程落地基础。

它的优势：

- V1 边界明确，聚焦“导入 -> LLM 拆解 -> 人工校正 -> 资产沉淀”。
- 已经包含 CSV 导入、纯文本导入、任务进度、模型状态、错误展示、待审核资产等当前已实现或正在实现的能力。
- 数据对象和非功能需求比较贴近现有后端。
- 有明确 Roadmap，可承接后续模板库、RAG、生成、评审、反馈、作者分析。

它的问题：

- 产品愿景偏窄，容易让系统被理解成“文案资产管理工具”，而不是“AI 文案拆解与创作系统”。
- 片段级拆解、手动组稿、推荐下一句、诊断与生成等能力只在 Roadmap 中出现，没有形成完整产品结构。
- 多知识库体系需要进一步整理成正式的信息架构。

### 2.2 `PRD_prat1.md`

当前 `PRD_prat1.md` 更像产品愿景稿。

它的优势：

- 产品目标更完整，包含拆解、检索、组稿、推荐、诊断、生成。
- 明确提出片段级拆解和上下文保留，这是后续 RAG 和推荐下一句的关键基础。
- 对“不要复制爆款，而是学习结构、节奏、论证方式和表达方向”的产品原则表达更好。

它的问题：

- MVP 范围过大，把素材库检索、手动组稿、推荐下一句、自动组稿、诊断、生成都放进第一版，会导致工程不可控。
- 数据对象、接口边界、审核流程、导入任务、错误处理不如 `PRD.md` 清晰。
- 没有把“原文案库、结构化拆解库、片段级拆解库、模板库、标签库、案例库、禁用库”整理成统一知识库体系。

## 6. 多知识库体系整理

完整产品版建议正式采用以下知识库结构：

### 6.1 原始文案库

保存原文和来源。

核心内容：

- 原始文案
- 来源链接
- 来源渠道/平台
- 作者名称
- 作者主页
- 作者粉丝数
- 表现指标
- 行业、人群、目的、风格
- 所属集合

### 6.2 结构化拆解库

保存每条文案的整体分析结果。

核心内容：

- 主题
- 目标用户
- 核心痛点
- 情绪按钮
- 开头钩子
- 内容结构
- 表达技巧
- 可复用模板
- 适用场景
- 风险提示
- 置信度
- 人工校正结果

### 6.3 片段级拆解库

保存连续片段、单句片段和上下文窗口。

核心内容：

- 来源文案 ID
- 来源分析 ID
- 片段顺序
- 前后片段
- 上下文窗口
- 片段文本
- 片段角色
- 片段位置
- 弱标签

这是后续“素材检索、推荐下一句、手动组稿”的关键库。

### 6.4 模板库

保存从已审核文案中抽象出来的句式和框架。

核心内容：

- 钩子模板
- 痛点表达模板
- 转折模板
- 证明模板
- CTA 模板
- 整篇结构模板
- 适用行业、人群、目的

### 6.5 标签库

保存系统稳定使用的标签体系。

核心内容：

- 行业
- 情绪
- 目的
- 人群
- 钩子类型
- 片段角色
- 风险等级

标签库不应在早期过度复杂，先用弱标签和人工校正沉淀。

### 6.6 案例库

保存高表现案例及其原因。

核心内容：

- 案例文案
- 表现指标
- 成功原因
- 可复用点
- 不可复刻点
- 适合参考的场景

### 6.7 禁用库

保存敏感词、违规表达、不要复刻的内容。

核心内容：

- 敏感词
- 违规表达
- 高风险承诺
- 侵权风险表达
- 不要复刻的原句
- 替代表达建议

## 7. 阶段规划

### Phase 1: 文案资产闭环

目标：先把原始文案稳定导入、拆解、校正、保存。

包含：

- CSV 导入
- 纯文本导入
- LLM 拆解
- 导入任务进度
- 待审核列表
- 详情查看
- 人工校正
- 审核状态
- 原始文案库
- 结构化拆解库
- 基础集合/知识库管理

不包含：

- 自动生成完整文案
- 推荐下一句
- 手动组稿工作台
- 向量检索
- Reranker

### Phase 2: 片段级素材库与基础检索

目标：让系统能把文案拆成可检索、可复用、带上下文的素材片段。

包含：

- 片段级拆解持久化
- 上下文窗口保存
- 片段角色、位置、行业等弱标签
- 基础结构化筛选
- 按来源文案查看片段

不包含：

- 高级语义检索
- 推荐下一句
- 自动组稿

### Phase 3: 手动组稿工作台

目标：让用户能从素材库中选择片段，手动组合成新文案草稿。

包含：

- 素材库列表
- 草稿编辑区
- 片段添加、删除、排序
- 草稿保存
- 版本保存

不包含：

- 自动生成完整文案
- 实时向量入库

### Phase 4: AI 推荐下一句

目标：根据当前草稿上下文，推荐下一句候选。

包含：

- 读取当前草稿上下文
- 判断下一句功能
- 检索相似上下文和后续片段
- 生成 3-5 个候选句
- 返回推荐理由和风险提示

依赖：

- 片段级素材库
- 基础检索
- 草稿上下文

### Phase 5: AI 自动组稿

目标：根据产品、人群、目的、平台、风格生成原创初稿。

包含：

- 创作需求解析
- 文案策略生成
- 结构规划
- 检索参考片段和模板
- 生成原创初稿
- 输出多个版本

原则：

- 不直接拼接原句。
- 素材库只作为结构和表达参考。
- 输出必须带原创风险提示。

### Phase 6: 文案诊断、原创改写与合规评审

目标：对用户文案或生成文案进行质量诊断、风险识别和改写。

包含：

- 开头吸引力诊断
- 目标人群清晰度诊断
- 痛点具体度诊断
- 上下文连贯性诊断
- 口播自然度诊断
- 转化动作诊断
- 原创风险诊断
- 违规风险诊断
- 修改建议
- 替换版本

原则：

- 弱化绝对分数。
- 使用分档和具体修改建议。
- 不把 AI 评分作为最终裁判。

## 9. 后端优先建设顺序

因为当前约定是前端由用户负责，后端应优先提供稳定接口和数据契约。

建议后端顺序：

1. 固化数据库主存储，减少 Redis/内存兜底对正式数据的影响。
2. 完善原始文案库和结构化拆解库。
3. 完善片段级拆解库。
4. 增加模板库、标签库、案例库、禁用库 CRUD。
5. 增加草稿和版本数据模型。
6. 增加基础素材检索接口。
7. 增加推荐下一句接口。
8. 增加自动组稿接口。
9. 增加诊断与改写接口。
10. 增加合规与原创风险接口。

## 10. 前端需要知道的边界

前端不应该直接理解 LLM 原始输出。

前端应依赖后端稳定 API：

- 导入任务接口只展示 `TaskResponse`。
- 文案资产列表只展示 `CopyAssetSummary`。
- 知识库列表使用各自独立接口。
- 草稿工作台只操作草稿、片段和推荐接口。
- AI 生成、诊断、改写都应通过后端任务接口异步执行。

对于长任务，前端统一使用：

1. 提交任务。
2. 获取 `task_id`。
3. 轮询任务状态。
4. 根据 `progress.phase`、`progress.percent`、`progress.current_message` 展示进度。
5. 完成后根据 `result` 拉取对应资源。

## 11. 主要风险

### 11.1 范围膨胀

完整产品版容易把所有能力都塞进第一阶段。

应对：

- PRD 允许完整，但验收必须分 Phase。
- 每个 Phase 都有独立可用结果。

### 11.2 片段过碎

如果只保存单句片段，后续推荐和组稿会缺上下文。

应对：

- 同时保存 `fragment_text` 和上下文窗口。
- 保留连续 span 的能力。

### 11.3 生成像拼接

如果生成直接复用素材原句，会有原创和质量风险。

应对：

- 明确素材只作为结构和表达参考。
- 生成结果必须经过原创风险提示。

### 11.4 标签体系过早复杂

早期强行定义大量标签会导致维护成本过高。

应对：

- 早期采用弱标签。
- 通过人工校正和案例积累逐步稳定标签库。

### 11.5 LLM 输出不稳定

LLM 可能返回类型错误、字段缺失或不符合 schema。

应对：

- 后端必须做结构化校验和安全归一化。
- 前端只消费后端 schema。
