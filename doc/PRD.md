# PRD: RagAgent AI 文案拆解与创作系统

## 1. 产品定位

RagAgent 是一个面向短视频、口播、种草、私域转化和营销文案创作的 AI 文案拆解与创作系统。

系统的长期目标不是简单复制爆款文案，而是帮助用户理解优秀文案背后的结构、节奏、论证方式、情绪调动和表达策略，并将这些能力沉淀成可检索、可复用、可校正的知识库。用户后续可以基于这些知识库完成素材检索、手动组稿、AI 推荐下一句、自动组稿、文案诊断、原创改写和合规评审。

当前产品采用“完整产品版”规划，但工程实现按阶段推进。第一阶段先建立稳定的文案资产闭环，避免在数据资产不可靠时过早投入生成和复杂 RAG。

## 2. 产品原则

- 先沉淀资产，再做生成。没有稳定、可校正、可复用的文案资产，后续检索和生成都会缺少可靠基础。
- 学习结构，不复制原句。素材库只作为结构、节奏、表达方式和论证路径的参考，不鼓励直接拼接原文。
- 弱标签优先，强体系后置。早期不要强行设计过细标签体系，应通过人工校正和案例积累逐步稳定。
- 人工校正是核心闭环。LLM 拆解结果必须允许人工审核、修改和沉淀。
- 长任务必须可见。导入、拆解、生成、诊断等任务都应有进度、阶段、模型和错误信息。
- 前端消费后端稳定 schema，不直接依赖 LLM 原始输出。

## 3. 目标用户

### 3.1 当前阶段用户

当前阶段主要面向项目作者和内部使用者。

用户特点：

- 能接受本地部署和手动启动服务。
- 能接受对 LLM 拆解结果做人工校正。
- 更关注文案资产质量和系统可扩展性，而不是完整商业化体验。
- 希望后续让 Agent 基于已沉淀资产继续生成、评审和优化内容。

### 3.2 长期目标用户

- 短视频运营
- 个人 IP 创作者
- 电商和私域转化团队
- 文案策划人员
- 内容营销团队

暂不把公开 SaaS、多租户权限、团队协作作为第一阶段目标。

## 4. 核心使用场景

### 4.1 文案资产沉淀

用户已经收集了一批高表现短视频、口播或种草文案，希望把这些文案导入系统，自动拆解为结构化资产，并通过人工校正沉淀到知识库中。

### 4.2 片段级素材检索

用户希望从已审核文案中查找可参考的片段，例如：

- 适合母婴减脂的共情型开头。
- 更有反差感的转折句。
- 低压力引导私信的结尾。
- 适合口播开场的痛点表达。

### 4.3 手动组稿

用户希望从素材库中选择片段，在草稿区手动组合、排序和编辑，形成一条新文案。

### 4.4 AI 推荐下一句

用户正在写一条文案，希望 AI 根据当前上下文、创作目标和素材库，推荐后续 3-5 个候选句。

### 4.5 AI 自动组稿

用户输入产品、人群、平台、风格和目的，系统参考知识库中的结构、模板和案例，生成一版或多版原创文案。

### 4.6 文案诊断与改写

用户写完文案后，希望 AI 判断文案存在的问题，给出修改建议、替换版本、原创风险和合规风险提示。

## 5. 产品完整闭环

完整闭环如下：

1. 导入原始文案。
2. 保存来源、作者、渠道、表现指标等元数据。
3. LLM 进行整体结构化拆解。
4. LLM 或规则进一步进行片段级拆解。
5. 用户人工校正整体分析和片段结果。
6. 审核后的内容进入多个知识库。
7. 用户通过筛选、检索或语义召回找到素材。
8. 用户手动组稿或调用 AI 辅助创作。
9. 系统对生成或用户输入文案进行诊断、改写和风险提示。
10. 用户反馈和表现数据回流，优化后续检索和生成策略。

## 6. 知识库信息架构

### 6.1 原始文案库

保存原文和来源，是所有后续拆解、检索和生成的基础。

核心字段：

- 原始文案
- 来源链接
- 来源渠道或平台
- 作者名称
- 作者主页
- 作者粉丝数
- 点赞、评论、收藏、转发等表现指标
- 行业
- 目标人群
- 内容目的
- 表达风格
- 所属集合
- 创建时间

### 6.2 结构化拆解库

保存每条文案的整体分析结果。

核心字段：

- 主题
- 目标用户
- 核心痛点
- 情绪按钮
- 开头钩子
- 内容结构
- 表达技巧
- 可复用模板
- 适用场景
- 风险提示
- 置信度
- 自动分析结果
- 人工校正结果
- 审核状态

### 6.3 片段级拆解库

保存连续片段、单句片段和上下文窗口，是后续素材检索、推荐下一句和手动组稿的关键库。

核心字段：

- 来源文案 ID
- 来源分析 ID
- 片段顺序
- 上一片段
- 下一片段
- 前置上下文
- 后置上下文
- 片段文本
- 片段角色
- 片段位置
- 行业
- 来源质量
- 风险等级

片段角色早期采用弱标签，例如：

- 钩子
- 痛点
- 解释
- 转折
- 证明
- 解决方案
- CTA

片段位置早期采用弱标签：

- 开头
- 中段
- 结尾

### 6.4 模板库

保存从已审核文案中抽象出来的句式和框架。

核心内容：

- 钩子模板
- 痛点表达模板
- 转折模板
- 证明模板
- CTA 模板
- 整篇结构模板
- 适用行业
- 适用人群
- 适用目的
- 来源追溯

### 6.5 标签库

保存系统稳定使用的标签体系。

核心内容：

- 行业
- 情绪
- 目的
- 人群
- 钩子类型
- 片段角色
- 风险等级

标签库早期不追求完整分类学，先满足筛选、人工校正和基础检索。

### 6.6 案例库

保存高表现案例及其原因。

核心内容：

- 案例文案
- 表现指标
- 成功原因
- 可复用点
- 不可复刻点
- 适合参考的场景
- 来源追溯

### 6.7 禁用库

保存敏感词、违规表达、不要复刻的内容。

核心内容：

- 敏感词
- 违规表达
- 高风险承诺
- 侵权风险表达
- 不要复刻的原句
- 替代表达建议

## 7. 阶段范围

### 7.1 Phase 1: 文案资产闭环

目标：把原始文案稳定导入、拆解、校正和保存。

包含：

- CSV 导入
- 纯文本导入
- 纯文本中的作者、平台、粉丝数等来源元数据抽取
- LLM 结构化拆解
- 导入任务进度
- 模型状态展示
- 行级错误展示
- 待审核列表
- 文案详情
- 人工校正
- 审核状态
- 原始文案库
- 结构化拆解库
- 基础集合管理

不包含：

- 自动生成完整文案
- 推荐下一句
- 手动组稿工作台
- 高级向量检索
- Reranker
- 作者分析
- 多用户权限

### 7.2 Phase 2: 片段级素材库与基础检索

目标：把已审核文案拆成可检索、可复用、带上下文的素材片段。

包含：

- 片段级拆解持久化
- 上下文窗口保存
- 片段角色和位置标签
- 来源文案追溯
- 基础结构化筛选
- 按文案查看片段

不包含：

- 推荐下一句
- 自动组稿
- 复杂语义召回

### 7.3 Phase 3: 手动组稿工作台

目标：让用户能从素材库中选择片段，手动组合成新文案草稿。

包含：

- 素材库列表
- 草稿编辑区
- 片段添加
- 片段删除
- 拖拽排序
- 手动编辑
- 草稿保存
- 版本保存

不包含：

- 草稿实时写入向量库
- 全自动生成
- 多人协作

### 7.4 Phase 4: AI 推荐下一句

目标：根据当前草稿上下文，推荐下一句候选。

包含：

- 读取当前草稿上下文
- 判断下一句承担的文案功能
- 检索相似上下文和后续片段
- 生成 3-5 个候选句
- 返回推荐理由
- 返回适合插入的位置
- 返回语气说明
- 返回原创风险提示

依赖：

- 片段级素材库
- 基础检索能力
- 草稿上下文

### 7.5 Phase 5: AI 自动组稿

目标：根据产品、人群、目的、平台、风格生成原创初稿。

输入：

- 产品
- 目标人群
- 内容目的
- 平台
- 风格
- 禁忌表达
- 文案长度

包含：

- 创作需求解析
- 文案策略生成
- 文案结构规划
- 检索参考片段和模板
- 生成原创初稿
- 输出多个版本
- 生成理由说明
- 原创风险提示

原则：

- 不直接拼接原句。
- 素材库只作为结构和表达参考。
- 输出必须可继续编辑和诊断。

### 7.6 Phase 6: 文案诊断、原创改写与合规评审

目标：对用户文案或生成文案进行质量诊断、风险识别和改写。

诊断维度：

- 开头吸引力
- 目标人群清晰度
- 痛点具体度
- 上下文连贯性
- 情绪共鸣
- 口播自然度
- 转化动作
- 原创风险
- 违规风险

输出方式：

- 弱化绝对数字分数。
- 使用分档判断，例如弱、一般、强、高风险。
- 给出具体修改建议。
- 指出哪一句需要改。
- 说明为什么需要改。
- 提供替换版本。

## 8. 核心功能需求

### 8.1 文案导入

系统支持两种导入方式：

- CSV 批量导入
- 纯文本单条导入

纯文本导入说明：

- 用户粘贴的内容可能同时包含正文和来源信息，例如作者、平台、粉丝数、来源链接、点赞数、收藏数等。
- 后端应让 LLM 或安全解析逻辑尝试从纯文本中抽取这些元数据，并写入文案资产字段。
- 无法可靠识别的元数据可以为空，不应阻塞正文导入和结构化拆解。
- 元数据抽取属于 Phase 1 的文案资产沉淀能力，不属于 Phase 2 的片段级素材库能力。
- Phase 1 只保存作者基础信息；作者画像、作者分析、跨文案作者聚合仍然不包含在 Phase 1。

CSV 字段约定：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `source_text` | 是 | 原始文案 |
| `source_url` | 否 | 文案来源链接 |
| `author_name` | 否 | 发布作者或账号名称 |
| `author_url` | 否 | 发布作者主页链接 |
| `author_follower_count` | 否 | 作者粉丝数 |
| `platform` | 否 | 平台，如小红书、抖音、视频号 |
| `industry` | 否 | 行业或赛道 |
| `audience` | 否 | 目标人群 |
| `purpose` | 否 | 内容目标，如引流、成交、涨粉 |
| `style` | 否 | 表达风格 |
| `likes` | 否 | 点赞数 |
| `comments` | 否 | 评论数 |
| `favorites` | 否 | 收藏数 |
| `shares` | 否 | 转发数 |

导入要求：

- `source_text` 为空的行不能导入。
- `author_follower_count` 如果存在，必须能解析为非负整数。
- 表现指标字段如果存在，必须能解析为整数。
- 单行失败不应影响其他有效行。
- 前端应展示行级错误。
- 纯文本导入时，LLM/解析逻辑应优先抽取 `author_name`、`author_url`、`author_follower_count`、`platform`、`source_url`、`likes`、`comments`、`favorites`、`shares` 等字段。

### 8.2 LLM 拆解

系统应对每条有效文案调用 LLM，输出结构化拆解结果。

拆解字段：

| 字段 | 说明 |
| --- | --- |
| `topic` | 文案主题 |
| `target_user` | 目标用户 |
| `core_pain` | 核心痛点 |
| `emotion_buttons` | 情绪按钮 |
| `hook` | 开头钩子 |
| `structure` | 内容结构步骤 |
| `expression_skills` | 表达技巧 |
| `reusable_template` | 可复用模板或句式 |
| `suitable_scenarios` | 适用场景 |
| `risk_warnings` | 风险提醒 |
| `confidence` | 拆解置信度，范围 0 到 1 |

后端必须校验 LLM 返回内容。对于常见格式偏差，例如把列表字段返回成字符串，后端可以做安全归一化，但对外 API 必须返回稳定结构。

### 8.3 导入任务进度

批量导入和需要 LLM 的任务都必须有任务状态。

任务状态至少包含：

- 当前阶段
- 使用模型
- 当前行
- 总行数
- 已处理数量
- 成功数量
- 失败数量
- 百分比进度
- 当前状态说明
- 行级错误

典型阶段：

- 等待
- 解析 CSV
- 调用 LLM
- 保存资产
- 完成
- 失败

### 8.4 文案资产列表

导入成功后，用户应能在资产列表中看到文案资产。

列表至少展示：

- 主题或原文摘要
- 作者名称
- 平台
- 行业
- 审核状态

列表应支持后续扩展筛选：

- 平台
- 行业
- 审核状态
- 集合

### 8.5 文案资产详情和校正

用户点击某条资产后，应看到：

- 原始文案
- 来源链接
- 作者名称、作者主页和粉丝数
- 平台、行业、人群、目的、风格
- 点赞、评论、收藏、转发等表现指标
- LLM 自动拆解结果
- 人工校正字段

用户应能校正以下核心字段：

- 主题
- 目标用户
- 核心痛点
- 情绪按钮
- 开头钩子
- 内容结构
- 表达技巧
- 可复用模板
- 适用场景
- 风险提示
- 置信度
- 审核状态

### 8.6 审核状态

至少支持三种审核状态：

- `pending_review`: 待审核
- `approved`: 已确认
- `rejected`: 已拒绝

默认导入成功后的资产状态为 `pending_review`。

### 8.7 素材检索

Phase 2 起支持素材检索。

基础检索优先使用 PostgreSQL 结构化筛选：

- 行业
- 片段角色
- 片段位置
- 来源质量
- 风险等级

后续增强可以加入：

- Milvus 语义向量召回
- LLM 或 Reranker 候选重排

### 8.8 草稿与组稿

Phase 3 起支持草稿和组稿。

草稿能力：

- 创建草稿
- 编辑草稿
- 添加素材片段
- 删除素材片段
- 调整片段顺序
- 保存版本

草稿不实时同步到向量库。只有用户确认沉淀为新素材时，才进入素材库和后续 embedding 流程。

### 8.9 生成、推荐和诊断

Phase 4 起逐步增加：

- AI 推荐下一句
- AI 自动组稿
- 文案诊断
- 原创改写
- 合规评审

这些能力应通过后端异步任务执行，并复用统一任务状态接口。

表示原始文案资产。

核心字段：

- 文案 ID
- 原文
- 来源链接
- 平台
- 作者信息
- 行业
- 目标人群
- 内容目的
- 表达风格
- 表现指标
- 所属集合
- 创建时间

### 9.2 CopyAnalysis

表示文案整体拆解结果。

核心字段：

- 所属文案 ID
- 自动拆解结果
- 人工校正结果
- 置信度
- 审核状态
- 创建时间
- 更新时间

### 9.3 CopyFragment

表示片段级素材。

核心字段：

- 片段 ID
- 来源文案 ID
- 来源分析 ID
- 顺序
- 前后片段
- 上下文窗口
- 片段文本
- 片段角色
- 片段位置
- 弱标签
- 创建时间

### 9.4 Template

表示可复用模板。

核心字段：

- 模板 ID
- 模板类型
- 模板内容
- 适用场景
- 来源追溯
- 创建时间

### 9.5 Tag

表示稳定标签。

核心字段：

- 标签 ID
- 标签类型
- 标签名称
- 描述
- 是否启用

### 9.6 Case

表示高表现案例及原因。

核心字段：

- 案例 ID
- 来源文案 ID
- 表现指标
- 成功原因
- 可复用点

### 9.8 Draft

表示用户草稿。

核心字段：

- 标题
- 创作目标
- 当前正文
- 片段引用
- 版本
- 创建时间
- 更新时间

### 9.9 Author

表示文案发布作者或平台账号。

Phase 1 可先随文案保存基础作者信息，后续再独立成作者分析对象。

核心字段：

- 作者 ID
- 作者名称
- 作者主页
- 所属平台
- 粉丝数
- 关联文案数量

### 9.10 ImportTask

表示一次导入任务。

核心字段：

- 任务 ID
- 任务状态
- 使用模型
- 当前阶段
- 当前行和总行数
- 成功数量
- 失败数量
- 行级错误
- 完成结果

## 10. API 与前端协作边界

后端负责：

- 文案导入
- LLM 调用
- 结构化校验
- 资产持久化
- 知识库 CRUD
- 任务状态
- 生成、推荐、诊断等长任务

前端负责：

- 文件读取和提交
- 导入进度展示
- 待审核列表展示
- 校正表单
- 草稿编辑体验
- 任务轮询
- 错误提示

前端不应该直接解析 LLM 原始输出。

长任务统一交互模式：

1. 前端提交任务。
2. 后端返回 `task_id`。
3. 前端轮询任务接口。
4. 前端根据 `progress.phase`、`progress.percent`、`progress.current_message` 展示进度。
5. 任务完成后前端根据 `result` 拉取对应资源。

## 11. 非功能需求

- 本地可运行，优先服务个人开发和验证。
- 长任务不能阻塞前端页面。
- LLM 调用失败时，错误必须可见。
- CSV 编码应优先兼容 UTF-8 和 UTF-8 BOM。
- 后端 API 返回结构必须稳定。
- 正式数据优先进入 PostgreSQL。
- Redis 和内存只能作为本地开发兜底或任务队列机制，不应作为正式主存储。
- 文案资产应能被 API 进程和 worker 进程共同访问。
- 作者信息应作为后续作者分析的基础数据保留。
- 测试环境不能依赖真实 LLM 网络调用，应使用 mock 或 fake。
- 文档、代码注释、配置文件中的中文应使用 UTF-8 编码。

## 12. 成功标准

### 12.1 Phase 1 成功标准

- 用户可以上传测试 CSV。
- 用户可以直接粘贴纯文本导入。
- 纯文本中包含作者、平台、粉丝数等来源信息时，系统能尽量抽取并保存到文案资产。
- 前端能显示导入任务进度和使用模型。
- 合法文案会逐条完成 LLM 拆解。
- 无效行会显示行级错误，不影响其他行。
- 导入成功的资产能显示在待审核列表中。
- 用户能查看原文、作者、平台、元数据、指标和拆解结果。
- 用户能校正拆解字段并保存审核状态。
- 后端测试通过。
- 前端构建通过。

### 12.2 完整产品成功标准

- 用户能稳定沉淀 100-300 条文案资产。
- 用户能从素材库中找到可用片段。
- 用户能手动组稿并保存版本。
- AI 推荐下一句基本能接上上下文。
- AI 自动组稿不是简单拼接原句。
- 文案诊断建议对修改有帮助。
- 生成结果有原创风险和合规风险提示。

## 13. 风险与应对

### 13.1 范围膨胀

风险：完整产品版容易把所有能力都塞进第一阶段。

应对：

- PRD 保留完整产品目标。
- 验收必须按 Phase 控制。
- 每个 Phase 都要有独立可用结果。

### 13.2 LLM 输出不稳定

风险：LLM 可能返回类型错误、字段缺失或不符合 schema。

应对：

- 后端做结构化校验。
- 对常见格式偏差做安全归一化。
- 前端只消费后端 schema。

### 13.3 片段过碎

风险：只保存单句片段会导致后续推荐和组稿缺上下文。

应对：

- 同时保存片段文本和上下文窗口。
- 保留连续 span 的能力。
- 检索时返回片段及其上下文。

### 13.4 生成结果像拼接

风险：如果生成直接复用素材原句，会有原创和质量风险。

应对：

- 素材只作为结构和表达参考。
- 生成结果必须经过原创风险提示。
- 禁止把素材片段直接拼成最终文案。

### 13.5 标签体系过早复杂

风险：早期强行定义大量标签会导致维护成本过高。

应对：

- 早期采用弱标签。
- 通过人工校正和案例积累逐步稳定标签库。

### 13.6 评分误导用户

风险：AI 评分容易被用户理解为绝对判断。

应对：

- 弱化数字分数。
- 使用分档和具体修改建议。
- 明确 AI 诊断是编辑辅助，不是最终裁判。

## 14. Roadmap

### Phase 1: 文案资产闭环

导入、拆解、校正、审核、持久化。

### Phase 2: 片段级素材库与基础检索

拆分片段、保存上下文、结构化筛选。

### Phase 3: 手动组稿工作台

素材选择、草稿编辑、片段排序、版本保存。

### Phase 4: AI 推荐下一句

基于上下文和素材库生成候选句。

### Phase 5: AI 自动组稿

基于产品、人群、平台、风格和知识库生成原创初稿。

### Phase 6: 文案诊断、原创改写与合规评审

质量诊断、修改建议、原创风险、违规风险、替换版本。

### 长期增强

- 作者分析
- 反馈回流
- 发布数据自动回流
- 多用户和团队协作
- 更高级的向量检索和重排
- LangGraph 策略编排

## 15. Open Questions

- Phase 1 单次 CSV 导入上限应固定为多少条。
- 作者信息什么时候从文案元数据升级为独立 Author 表。
- 模板库是人工沉淀优先，还是 LLM 自动抽象优先。
- Phase 2 是否先只做结构化筛选，还是同步引入向量检索。
- 文案诊断是否需要保存历史诊断记录。
- 禁用库的风险等级和规则来源如何维护。
